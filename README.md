# Задание 1. Множество Мандельброта (2 балла)

## Постановка задачи

Разработать параллельную программу для нахождения заданного количества точек множества Мандельброта.

**Входные данные:** `./program nthreads npoints`, где `nthreads` — количество потоков, `npoints` — количество точек.

**Выходные данные:** CSV-файл с координатами найденных точек.

Множество Мандельброта определяется последовательностью:

$$
z_{n+1}=z_n^2+c,\quad z_0=0
$$

Число $c$ принадлежит множеству, если для всех $n$ выполняется условие $|z_n|<2$.

## Реализация

Программа написана на C с использованием библиотеки **Pthreads**. Алгоритм основан на случайной генерации точек и проверке их принадлежности множеству Мандельброта.

Каждый поток независимо генерирует координаты в области $x\in[-2;1]$, $y\in[-1;1]$ с помощью `rand_r()`, используя собственное состояние генератора случайных чисел.

Для каждой точки функция `is_in_mandelbrot()` вычисляет последовательность $z_{n+1}=z_n^2+c$, отдельно рассчитывая действительную и мнимую части:

```math
Re(z_{n+1}) = Re(z_n)^2 - Im(z_n)^2 + x
```

```math
Im(z_{n+1}) = 2Re(z_n)Im(z_n) + y
```

Если квадрат модуля комплексного числа достигает 4, точка отклоняется. Если за `MAX_ITER = 1000` итераций этого не происходит, точка принимается как принадлежащая множеству (приближённая проверка).

Для уменьшения затрат на синхронизацию используется **пакетная обработка** (`BATCH_SIZE = 100`). Каждый поток проверяет 100 кандидатов, сохраняет подходящие точки в локальный массив `local_points`, после чего записывает их в общий CSV-файл.

Доступ к общему счётчику `global_points_count`, флагу завершения `stop_flag` и запись в файл защищены мьютексом `pthread_mutex_t`. Когда количество записанных точек достигает `npoints`, устанавливается `stop_flag = 1`, после чего потоки завершают работу.

Потоки создаются через `pthread_create()`, а их завершение ожидается через `pthread_join()`. Результаты сохраняются в `csv_results/set_nthreads_npoints.csv`.

# Задание 2. N-body: параллельная симуляция задачи N тел на pthreads

Программа на C считает траектории `N` материальных точек, которые притягиваются по закону всемирного тяготения. Время интегрируется методом Эйлера 1 порядка, вычисления распараллелены с помощью POSIX threads.

Реализованы две версии, которые отличаются способом раздачи работы между потоками:

* `nbody.c` — **статическая циклическая** раздача строк (заранее, потоки берут через одну);
* `nbody_dyn.c` — **динамическая** раздача строк (потоки берут работу из общего счётчика).

## Содержимое репозитория

| Файл | Назначение |
|---|---|
| `nbody.c` | программа со статической раздачей строк |
| `nbody_dyn.c` | программа с динамической раздачей строк |
| `timer.h` | макрос `GET_TIME` для замера времени (`gettimeofday`) |
| `input.txt` | пример входных данных (Солнце и Земля) |
| `input5000.txt` | входные данные с 5000 телами для экспериментов |
| `results_visual.py` | скрипт, строящий графики из результатов замеров |
| `graphs` | папка с графиками времени и ускорения и другими|

## Сборка

```bash
gcc -O2 -pthread nbody.c -o nbody -lm
gcc -O2 -pthread nbody_dyn.c -o nbody_dyn -lm
```

Нужны `gcc` и `libpthread`. Проверено на Ubuntu 22.04 (WSL2).

## Запуск

```bash
./nbody     tend input.txt [dt] [nthreads]
./nbody_dyn tend input.txt [dt] [nthreads] [stride] [chunk]
```

| Параметр | Описание | По умолчанию |
|---|---|---|
| `tend` | конечное время моделирования | обязательный |
| `input.txt` | файл с начальными данными | обязательный |
| `dt` | шаг по времени | `3600` |
| `nthreads` | число потоков | `4` |
| `stride` | писать в CSV каждый `stride`-й шаг | `1` |
| `chunk` | только `nbody_dyn`: сколько строк поток берёт за один раз | `1` |

Время работы вычислительной части печатается в `stderr`.

### Формат входного файла

Первая строка: число точек `n`. Далее `n` строк по 7 чисел:

```
масса  x  y  z  vx  vy  vz
```

Пример (Солнце и Земля):

```
2
1.989e30 0 0 0 0 0 0
5.972e24 1.496e11 0 0 0 2.978e4 0
```

Запуск примера (файл с 5000 тел, 10 часов=36000 секунд, шаг моделирования - один час, на 4 потоках):

```bash
./nbody 36000 input5000.txt 3600 4
```

### Формат выходного файла

Результат записывается в `out.csv`. Каждая строка соответствует одному моменту времени:

```
t x1 y1 x2 y2 ... xn yn
```

Первая строка соответствует `t = 0`. Расчёт ведётся в трёх измерениях (но z = 0), но в файл выводятся только координаты `x` и `y`.

## Алгоритм

Сила, действующая на тело `q` со стороны остальных тел:

```
F_q = G * m_q * sum_{k != q} m_k / |r_k - r_q|^3 * (r_k - r_q),   G = 6.67430e-11
```

Каждый шаг по времени `dt` состоит из двух этапов (метод Эйлера):

1. Вычислить силы `F` по текущим положениям тел.
2. Обновить положения и скорости:
   * `x += vx * dt`
   * `vx += F / m * dt`

Положение обновляется по старой скорости, затем обновляется скорость.

## Параллельная реализация

Общее для обеих версий:

* **Третий закон Ньютона.** Сила взаимодействия пары тел вычисляется один раз и прибавляется к одному телу и вычитается у другого. Это вдвое сокращает число вычислений (`j` пробегает значения от `i + 1`).
* **Гонка данных.** Из-за третьего закона разные потоки могут менять силу одного и того же тела. Чтобы не использовать мьютексы, у каждого потока свой массив сил. На втором этапе силы суммируются по всем потокам.
* **Синхронизация.** На каждый шаг приходится два барьера (`pthread_barrier_t`): первый после вычисления сил (нельзя двигать тела, пока кто-то ещё читает старые положения), второй после обновления тел (нельзя начинать новый шаг, пока не все тела обновлены).
* **Вывод.** Запись в файл выполняет только поток 0, чтобы строки не перемешивались.

Различие версий — как строки внешнего цикла по `i` распределяются между потоками. У ранних строк пар больше, чем у поздних, поэтому простое разбиение на непрерывные блоки дало бы неравную нагрузку.

### Статическая раздача (`nbody.c`)

Строки раздаются потокам циклически и заранее: поток `r` обрабатывает строки `r, r + nthreads, r + 2*nthreads, ...`. Нагрузка выравнивается, но если какой-то поток работает медленнее (например, попал на менее производительное ядро), остальные ждут его на барьере.

### Динамическая раздача (`nbody_dyn.c`)

Есть общий атомарный счётчик `next_row`. Поток вызывает `atomic_fetch_add(&next_row, chunk)`, получает номер первой строки своей пачки из `chunk` строк, обрабатывает её и берёт следующую, пока строки не кончатся. Атомарность операции гарантирует, что две одинаковые пачки не достанутся разным потокам, а мьютекс не нужен. Быстрые ядра успевают взять больше строк, медленные меньше, поэтому простоев на барьере становится меньше.

После первого барьера поток 0 сбрасывает счётчик в 0 для следующего шага. В этот момент счётчик никто не читает, а новый шаг начнётся только после второго барьера.

Из-за динамической раздачи порядок сложения сил в разных запусках может немного отличаться, поэтому последние знаки результата могут слегка меняться от запуска к запуску, это свойство вычислений с плавающей точкой.

## Проверка корректности

На тесте Солнце-Земля (`tend = 3.15e7`, `dt = 3600`):

* Через один шаг Земля сместилась по `y` ровно на `29780 * 3600 = 107 208 000` м, как и ожидается.
* К концу года Земля находится на расстоянии около `1.5e11` м от Солнца, то есть почти на исходной орбите. Небольшое отклонение объясняется погрешностью метода Эйлера.
* Солнце немного смещается под действием Земли, что подтверждает работу третьего закона Ньютона.
* Результаты запусков с 1 и 2 потоками полностью совпадают (`diff` не выдаёт различий).
* Динамическая версия на этом тесте даёт ту же последнюю строку `out.csv`, что и статическая.

# Задание 3. Блокировка чтения-записи (Read-Write Lock) на pthreads

## Постановка задачи

Разработать собственный тип данных для блокировки чтения-записи (`my_rwlock_t`) и соответствующие функции захвата/освобождения с использованием базовых примитивов библиотеки POSIX Threads (`pthread_mutex_t` и `pthread_cond_t`).

**Цели работы:**
- Реализовать примитив синхронизации `my_rwlock_t` с функциями инициализации, уничтожения, захвата на чтение/запись и освобождения.
- Апробировать разработанную структуру на задаче многопоточного доступа к отсортированному односвязному списку (`pth_ll_rwl.c`).
- Провести серию замеров производительности и сопоставить скорость работы собственной реализации со стандартной библиотечной блокировкой `pthread_rwlock_t`.

## Реализация

В рамках работы спроектирована структура `my_rwlock_t`, использующая паттерн **приоритета писателей (writer-preference)** для предотвращения их голодания.

### Структура данных

```c
typedef struct {
    pthread_mutex_t mutex;        // защита внутренних счетчиков от гонки данных
    pthread_cond_t  read_cond;    // условная переменная для очереди читателей
    pthread_cond_t  write_cond;   // условная переменная для очереди писателей
    int             readers;      // количество активных читателей
    int             writers;      // флаг активного писателя (0 или 1)
    int             wait_readers; // количество ожидающих читателей
    int             wait_writers; // количество ожидающих писателей
} my_rwlock_t;
```

### Алгоритм работы

1. **Захват на чтение (`my_rwlock_rdlock`):**
   - Поток захватывает `mutex`.
   - Проверяется условие: `while (rw->writers > 0 || rw->wait_writers > 0)`. Если есть активный или хотя бы один ожидающий писатель, читатель увеличивает `wait_readers` и усыпляется на `read_cond`. Это предотвращает монополизацию ресурса читателями.
   - Использование цикла `while` защищает от ложных пробуждений (*spurious wakeups*).
   - После выхода из цикла читатель инкрементирует `readers++` и освобождает `mutex`.

2. **Захват на запись (`my_rwlock_wrlock`):**
   - Писатель захватывает `mutex` и инкрементирует `wait_writers++`.
   - В цикле `while (rw->readers > 0 || rw->writers > 0)` поток ожидает полного освобождения ресурса на `write_cond`.
   - При освобождении списка писатель декрементирует `wait_writers--`, устанавливает `writers = 1` и отпускает `mutex`, получая монопольный доступ.

3. **Освобождение блокировки (`my_rwlock_unlock`):**
   - Поток захватывает `mutex` и декрементирует соответствующий счетчик (`readers--` или `writers = 0`).
   - **Раздельное пробуждение:**
     - Если `wait_writers > 0` и читателей больше нет (`readers == 0`), через `pthread_cond_signal(&rw->write_cond)` точечно пробуждается один писатель.
     - Если ожидающих писателей нет, но `wait_readers > 0`, через `pthread_cond_broadcast(&rw->read_cond)` одновременно пробуждаются все накопленные читатели (так как чтение допускает параллельный доступ).

### Условная компиляция

В исходном коде `pth_ll_rwl.c` организована условная компиляция через `#ifdef USE_MY_RWLOCK`:

```c
#ifdef USE_MY_RWLOCK
    #define RWLOCK_T        my_rwlock_t
    #define RWLOCK_INIT     my_rwlock_init
    #define RWLOCK_RDLOCK   my_rwlock_rdlock
    #define RWLOCK_WRLOCK   my_rwlock_wrlock
    #define RWLOCK_UNLOCK   my_rwlock_unlock
    #define RWLOCK_DESTROY  my_rwlock_destroy
#else
    #define RWLOCK_T        pthread_rwlock_t
    #define RWLOCK_INIT     pthread_rwlock_init
    #define RWLOCK_RDLOCK   pthread_rwlock_rdlock
    #define RWLOCK_WRLOCK   pthread_rwlock_wrlock
    #define RWLOCK_UNLOCK   pthread_rwlock_unlock
    #define RWLOCK_DESTROY  pthread_rwlock_destroy
#endif
```

Это позволяет собирать два независимых бинарных файла (`pth_ll_rwl_sys` и `pth_ll_rwl_my`) из единого исходного кода без его дублирования.

## Анализ результатов

1. **Поведение на 1–2 потоках:**  
   Пользовательская реализация `my_rwlock_t` не уступает стандартной `pthread_rwlock_t` или опережает её (до 13.8% при смешанной нагрузке). В условиях низкого уровня конкуренции накладные расходы на собственный мьютекс и условные переменные минимальны, а алгоритм быстро отдает приоритет ожидающим операциям.

2. **Поведение на 4–8 потоках:**  
   При масштабировании числа потоков библиотечная блокировка `pthread_rwlock_t` выходит вперед (на 8 потоках она быстрее на 43.7–47.6%). Причина разницы — архитектурная:
   - В `my_rwlock_t` все потоки (и читатели, и писатели) обязаны захватывать один и тот же внутренний `pthread_mutex_t` для изменения счетчиков при каждом входе и выходе. Под высокой нагрузкой этот мьютекс сам становится «бутылочным горлышком».
   - Системная `pthread_rwlock_t` в `glibc` оптимизирована на уровне низкоуровневых атомарных инструкций (`CAS`) и системного вызова Linux `futex`, не требуя тяжелого вспомогательного мьютекса при бесконфликтном параллельном чтении.

3. **Влияние характера нагрузки:**  
   Увеличение доли модифицирующих операций (вставка/удаление) с 1% до 20% замедлило общее время выполнения более чем в 15 раз на обоих типах блокировок. Это подтверждает монопольный характер операций записи, сериализующих доступ и блокирующих параллельное чтение на время перелинковки узлов списка.

## Вывод

- Реализация `my_rwlock_t` обеспечивает полную потокобезопасность: данные в связанном списке не повреждаются, а взаимоблокировки отсутствуют.
- Стратегия приоритета писателей (*writer-preference*) успешно предотвращает голодание пишущих потоков даже при преобладающем потоке читателей.
- На малом числе потоков (до 2) пользовательская реализация конкурентоспособна, однако при высокой параллельности (4–8 потоков) системная блокировка `pthread_rwlock_t` масштабируется эффективнее благодаря отсутствию единой точки синхронизации на внутреннем мьютексе.
